# 行为路由与指令覆盖验收

用于审核 Skill 是否不仅“格式正确”，而且能被模型在正确场景加载并稳定执行。

## 1. 正向引导

优先描述模型应该做什么，而不是反复列出不能做什么。

- 差：`不要猜、不要跳过验证、不要直接修改。`
- 好：`先读取日志形成根因假设；修改后重现原场景，并以实际输出作为完成证据。`

`Do not` 只保留给真正的安全边界、不可逆操作和相邻 Skill 排除条件。普通流程用目标动作、顺序和成功标准表达。反复点名错误行为会让它在上下文中更显著，不能替代正向工作流。

## 2. 检查负空间

Skill 没写的决策不会保持“中立”，而是交给模型先验。逐项检查：

1. 输入不完整时做什么？
2. 有多个实现路径时，谁决定、按什么原则决定？
3. 工具失败或证据不足时，是换验证路径、阻断，还是继续猜？
4. 修改后验证什么，失败是否阻止“完成”？
5. 与相邻 Skill 同时命中时，谁优先？

每个空白必须被分类为：

- **补齐**：不同选择会改变安全性、结果或外部副作用。
- **明确分支**：允许模型依据上下文选择，并给选择标准。
- **刻意开放**：实现细节可自由调整，不影响合同。

不要为了填空把 Skill 写成百科；只补会改变行为的缺口。

## 3. 行为路由测试矩阵

修改 description、When to Use、When Not to Use 或冲突规则后，至少准备以下样例：

| 组别 | 最少样例 | 预期 |
|---|---:|---|
| 明确正例 | 2 | 目标 Skill 被选中 |
| 口语/简称正例 | 1 | 不依赖正式术语也能选中 |
| 相邻负例 | 2 | 目标 Skill 不加载 |
| 冲突例 | 2 | 在最可能混淆的两个 Skill 间选对 |
| 加载后执行例 | 1 | 不只选对，还按核心流程执行 |

优先使用真实用户说法和历史误触发案例，不要只拿 description 原句改写后自测。

## 4. 验证层级

### 静态路由审查（每次必做）

- 正例的“动词 + 对象 + 输入类型”能在 description 找到依据。
- 负例由 When Not to Use 或冲突规则排除。
- 正文承诺的能力没有超出 description 范围。
- Hermes 不支持的第三方调用字段（如 `disable-model-invocation`、`allow_implicit_invocation`）不能作为路由门禁证据。

### 真实调用抽样（以下情况必做）

- 用户反馈过不触发或误触发。
- 修改了 frontmatter description。
- 新增或重命名 Skill。
- 与现有 Skill 存在明显语义重叠。

在新会话或隔离测试会话中运行样例，记录：输入、候选、实际加载、是否按核心流程执行。当前会话已预加载Skill时，不能拿它证明自动路由成功。

## 5. 通过标准

- 正例全部命中。
- 相邻负例无误触发。
- 冲突例路由符合显式优先级。
- 加载后执行例完成核心动作，而不是只复述Skill。
- 失败样例转化为最小修改后重测；不能用继续堆关键词掩盖范围重叠。

行为测试未执行时，只能报告“静态结构通过”，不能声称“触发准确率已验证”。
