# 脚本化决策门禁

目标：把确定性的机械执行交给脚本，把语义理解、方案选择和异常决策留给 Agent。脚本化不是目的；**降低重复劳动、执行漂移和人为遗漏**才是目的。

## 1. 第一性原理

LLM 擅长理解模糊意图和处理开放分支，但不擅长每次都以完全相同的顺序完成大量机械步骤。脚本擅长确定性执行和结构化验收，但会把错误假设固化成稳定错误。

因此不采用“凡是能写脚本就必须写脚本”的绝对规则，而采用：

> **重复、确定、可验证、人工执行易漂移的机械步骤优先脚本化；语义判断、探索和异常决策保留给 Agent。**

## 2. 判断矩阵

出现以下特征越多，越应该脚本化：

| 特征 | 判断问题 |
|---|---|
| 重复性 | 同一流程会再次执行，或一次要处理多个同类对象吗？ |
| 确定性 | 相同输入是否应得到相同结果/状态转换？ |
| 结构化 | 输入、输出、退出状态能否清楚定义？ |
| 易错性 | 手工复制命令、分页、计数、路径替换是否容易漏项或顺序漂移？ |
| 可验证性 | 能否用断言、hash、schema、集合差、HTTP状态或测试fixture验收？ |
| 规模效应 | 对象数量、文件数量或步骤数量是否使人工逐项执行成本明显上升？ |

### 强制脚本化

同时满足“确定性 + 可验证”，并具备以下任一项：

- 批量/分页/多文件处理，人工执行容易漏项。
- 同一机械流程预计重复执行。
- 安全扫描、schema校验、集合对账、hash、计数等确定性验证。
- 多条命令必须保持固定顺序，漏一步会造成错误或漂移。
- 需要稳定日志、退出码或结构化结果供后续流程消费。

### 优先脚本化但可例外

- 当前只执行一次，但步骤多、容易复制错误，未来可能复用。
- Agent仍需判断分支，但每个分支内部有稳定机械步骤。
- 外部接口尚在变化，可先保留薄脚本并明确契约来源和失效条件。

### 不应为了脚本化而脚本化

- 一次性、低风险、两三步即可完成，写脚本的维护成本高于执行成本。
- 核心工作是语义判断、内容评价、架构取舍或开放式探索。
- 输入输出契约尚未稳定，脚本只会固化未经验证的假设。
- 现有官方CLI、项目脚本或Skill包内脚本已经覆盖；应复用或修复canonical实现，不再造第二份。
- 脚本的唯一作用是绕开权限、安全策略或授权门禁。

## 3. 推荐架构

```text
Agent：理解目标 → 选择方案 → 确认高风险动作 → 处理异常
Script：读取结构化输入 → 执行确定步骤 → 记录日志 → 输出结构化结果/退出码
Agent：读取证据 → 判断结果 → 决定修复、回滚或交付
```

脚本不能取代 Agent 对以下事项的责任：

- 判断脚本是否适用于当前场景。
- 核对输入范围、权限和副作用。
- 解释异常结果，不能把非零退出码机械归因。
- 独立验收脚本产物，不能相信脚本自报“success”。

## 4. 脚本质量合同

Skill新增或采用脚本时至少检查：

1. **Canonical**：只有一个权威实现；先搜索已有脚本，禁止复制形成分叉。
2. **Interface**：参数、输入、输出、退出码明确；缺少必需参数时立即失败。
3. **Secrets**：密钥从环境变量/受控配置读取，不写入脚本、参数示例或日志。
4. **Safety**：高风险写操作保留数字确认；脚本化不等于获得授权。支持时提供 `--dry-run`。
5. **Idempotency**：可重复执行时应幂等；无法幂等必须明确重复执行后果和恢复方式。
6. **Observability**：关键路径有时间戳、级别、对象和结果；错误不得静默吞掉。
7. **Verification**：至少有语法/静态检查，并用正常、失败、边界样本真实运行；外部副作用用fixture、临时目录、mock或沙箱隔离。
8. **Official Contract**：涉及外部工具/API时锚定官方文档与查证日期。
9. **Portability**：明确运行环境、依赖、路径解析；不要依赖调用者碰巧处于某个工作目录。
10. **Completion Rule**：脚本与产物验证未通过，不得报告任务完成。

## 5. Skill Doctor评分归属

此门禁不新增第13维：

- **第7维 工作流**：检查机械流程是否该脚本化、是否复用canonical脚本、Agent/脚本职责是否合理。
- **第9维 验证闭环**：检查脚本是否有结构化证据、真实fixture、失败路径和完成阻断。
- **第11维 硬规则/Checklist**：高风险副作用是否仍经过授权、dry-run、回滚检查；不能因脚本化跳过。
- **第12维 日志与可观测性**：脚本关键路径和错误是否可追踪。

判定建议：

- ✅ 机械核心已合理脚本化，或任务不适合脚本化且理由成立；脚本质量合同与验证充分。
- ⚠️ 存在重复/易错机械步骤但规模较小，或已有脚本缺少部分接口、日志、幂等/验证合同。
- ❌ 批量、重复、确定性高且易漏的流程仍依赖Agent逐条手工执行；存在多个脚本分叉；或脚本无失败阻断、绕过授权/安全门禁。

## 6. 典型例子

适合脚本化：

- 扫描全部Profile的Skill路径、同名组、hash与运行时可见性。
- 批量校验YAML/frontmatter、Markdown围栏、引用存在性和schema。
- 文件清单对账、分页游标遍历、备份hash和数据库integrity_check。
- 固定API调用链、稳定格式转换、重复部署前检查。

保留给Agent：

- 判断两个Skill是否语义冲突。
- 判断warning是真缺陷还是启发式误判。
- 选择长期架构、临时方案或回滚路径。
- 评价文章质量、视觉设计和业务价值。
